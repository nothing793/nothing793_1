## 1. 本目录是什么

第 3 问要求 *"query program on top of your **inverted file** index"* —— 索引必须落盘、查询程序独立读盘，
所以结构是「建索引程序 + 查询程序」，中间靠 `index.bin` 连接。第 1 问的统计与第 2 问的建索引
必须共用同一套切词 / 词干化口径，因此合并成一个 `index_gen`（**两遍扫描**：pass 1 统计出 stoplist，
pass 2 跳过停用词建索引）。

**本目录交付的源文件只有两个**：`index_gen.c`（建索引）与 `query.c`（查询），词干算法
`stem.c` / `stem.h` 是外部引用。两者共用的索引模块（内存索引 + `index_save()` / `index_load()`
+ `index.bin` 格式规范）整体放在 [`index.h`](index.h) 里、函数写成 `static inline`，
两个程序各 `#include` 一次 —— 既有"格式只定义一处、不可能建的时候一套读的时候另一套"的好处，
又不用再维护一个 `index_io.c`。切词（原 `tokenize` 程序）也已并入 `index_gen.c`，
`index_gen` 直接读原始文本，`file.txt` 不再是必需的中间产物。历史沿革见第 13 节。

**现状：题面四问全部实现，端到端测试 21 项全过。**
`index_gen` 直接读语料（每个输入文件 = 一篇文档），先统计 θ 停用词（`stoplist.txt`），
再跳过停用词建索引并落盘 `index.bin`；`query` 独立加载 `index.bin`，支持单词 / 多词 AND /
短语查询，以及查询阈值 τ。

本机实测（gcc 11 / x86-64）：

| 语料 | 三元组 | N | V | index.bin | `index_gen` | `query` |
| --- | --- | --- | --- | --- | --- | --- |
| 合成语料（40 篇 × 4000 词，`tests/gen_corpus.py`，θ = 0.5） | 161,892 | 40 | 7,124 | 263.8 KB | 0.79 s | 0.02 s |
| 早期手写样例（未剔除停用词） | 880,000 | 40 | 26,376 | 3.6 MB | 1.3 s | 0.13 s |

**还差的一步**：真实语料（莎士比亚全集，`shakespeare.mit.edu`）按你的指示尚未下载。
拿到之后只要 `./index_gen <每部剧一个文件>`，其余流程与阈值实验原样复用（`tests/sweep.py` 不用改）。

## 2. 文件清单与状态

| 文件 | 职责 | 状态 |
| --- | --- | --- |
| `index.h` | **共享索引模块（单头文件库）**：公共类型（`DocTable` / `Position` / `Posting` / `inverted_index`）、接口、`index.bin` 格式规范，以及全部实现（`static inline`） | 就绪 |
| `index_gen.c` | 切词（`tokenize_document()`）+ Part 1（`collect_stats()` 统计 cf/df、`stoplist_build()` 按 `df/N > θ` 挑停用词、词频报告）+ Part 2（建内存索引 + `index_save()` 落盘）+ `main` | 完成 |
| `query.c` | Part 3：`index_load()` + 单词 / AND / 短语查询；Part 4：查询阈值 τ + `main` | 完成 |
| `stem.c` / `stem.h` | 词干模块（Porter 算法，`stemword()` = 转小写 + 词干），**外部引用**，两个程序都链它 | 就绪 |
| `tests/` | 端到端测试、合成语料生成、独立对拍、θ/τ 实验；详见 [`tests/README.md`](tests/README.md) | 完成 |

已移除的文件（内容都并进了上面两个源文件，沿革见第 13 节）：

- `index_io.c` → 并入 `index.h`；
- `tokenize.c` / `tokenize.h` / `tokenize_main.c` → 并入 `index_gen.c`；
- `wordcount.c`（只有空壳）、`file.txt`（旧中间产物，现在需要时由 `--dump-tokens` 按需产生）。

`index_gen` 与 `query` 各有一个 `main`，但共用同一个 `index.h`：「建索引」和「读索引」走
**同一套插入逻辑与同一个文件格式**，所以不可能出现"建的时候一套、读的时候另一套"。
与"拆成 index_io.c + 两个 .c"相比，差别只是把实现放进了头文件、由两个 `.c` 各包含一次
（`static inline`，见第 14 节）；与"各写一份拷贝"相比，差别是**格式规范在磁盘上仍然只有一份**。

## 3. 构建与运行

```bash
cd code

# 切词 + Part 1 + Part 2：统计 -> stoplist.txt -> 建索引 -> index.bin
gcc -std=c99 -Wall -Wextra -o index_gen index_gen.c stem.c -lm
./index_gen corpus/*.txt             # 每个文件 = 一篇文档，doc_id 按命令行顺序 0,1,2...
./index_gen --theta=0.4 corpus/*.txt # 运行时覆盖 θ
./index_gen --count-only corpus/*.txt   # 只跑 Part 1：词频报告 + stoplist.txt，不建索引
./index_gen --dump-tokens=file.txt corpus/*.txt  # 顺便写出三元组流（测试对拍用）
./index_gen - < play.txt             # 用 - 从 stdin 读一篇文档（先抄进临时文件，因为要读两遍）

# Part 3 + Part 4：查询
gcc -std=c99 -Wall -Wextra -o query query.c stem.c -lm
./query wevafi               # 单词查询
./query wevafi zebra         # 多个参数 = AND（交集）
./query "a b c"              # 单个参数含空白 = 短语（位置连续）
./query --tau=0.2 wevafi     # 开查询阈值
./query                      # 读 test.txt，每行一个查询
```

`index_gen` 只接受语料文件路径；`query` 只用**当前工作目录**下的相对路径
（`index.bin` / `stoplist.txt` / `test.txt` / `output.txt`），不认路径参数；
数据文件与可执行文件放在同一个目录即可。
θ 有三种给法：改 `index_gen.c` 里的 `STOPWORD_THETA` 宏、编译时 `-DSTOPWORD_THETA=0.4`、
运行时 `--theta=0.4`（宏只是默认值）。若还没有 `index.bin`，`./query` 会提示先跑 `./index_gen`；
若 `index.bin` 损坏或版本不符，`./query` 会拒绝加载并报错（不会带着半个索引继续查）。

测试与实验都在临时目录里编译执行，不往 `code/` 里丢产物：

```bash
cd tests
sh run_tests.sh                 # 19 项端到端测试（默认工作目录 /tmp/pr1-test）
python3 sweep.py /tmp/pr1-test  # θ / τ 敏感性实验，输出 Markdown 表
```

注意：仓库根目录的 `stmr.c` / `stmr.h` 是算法上游对照，**不要**和 `stem.c` 一起编译
（`stem` 符号会重复定义）。

## 4. 数据流与已实现的索引结构

```
原始文本 ──┬─ index_gen pass 1 ──> stoplist.txt（Part 1）
           └─ index_gen pass 2 ──> index.bin（Part 2）
                                     │
test.txt ─────────────────────────> query ──index_load()──┘ ──> output.txt（Part 3/4）
```

（加 `--dump-tokens` 时 pass 1 会额外写出一份 `file.txt` 三元组流，只为测试对拍，与流水线无关。）

两遍扫描的分工：pass 1 用 `run_pass(..., skip=NULL, ...)` → `tokenize_document()` 把整份语料
插进内存索引（顺便得到 cf / df），据此算出 stoplist；pass 2 **丢掉** pass 1 的索引、重新建一份
并跳过停用词，这样两份索引不会同时驻留。两遍共用同一个 `tokenize_document()` 与
`index_add_position()`，所以"统计"和"建索引"在切词、词干化、去重、排序上的口径不可能不一致。

内存结构（在 `index.h` 里，`index_gen` 与 `query` 共用同一份实现）：

- **`djb2` 哈希**（`hashsize` = 1000007 个桶）+ 链地址法；每个词干一个 `Posting`，
  挂一条按 `(doc_id, pos)` **升序**的 `Position` 链 —— df、求交、短语验证都依赖这个有序性；
- **去重键是 `(词干, doc_id, pos)`**：同一文档同一位置的同词干只保留一条；
- **词干化在建索引时做**（`stemword()` = 转小写 + Porter），所以 `run` / `runs` / `running` / `RUNS`
  并入同一个词干 `run`；查询词走同一个函数，因此查 `Running` 也能命中；
- 读入用 `while (fscanf(...) == 3)`，`doc_id` / `pos` 为负的行跳过并计数。

实测一个关键尺寸（本机 gcc 11 / x86-64）：

- `sizeof(inverted_index)` = **8,000,056 B ≈ 7.6 MB** —— `buckets` 是嵌在结构体里的定长数组。
  **必须堆分配**（`index_create()`）：放栈上会和调用者栈帧一起超过默认 8 MB 栈上限，直接段错误（已实测崩溃）。

## 5. 索引文件格式 `index.bin`（v1，已落地）

**权威规范是 `index.h` 顶部注释**，读写两侧都以那份注释为准；本节说明它的形状与取舍。

| 区段 | 内容 | 与目标设计的关系 |
| --- | --- | --- |
| 头部 64 B | 魔数 `PR1IDX`、版本、头部长度、文档数 / 词条数 / 位置总数、docs / terms / postings 三段偏移 | 设计稿里没写头部；落盘格式必须有版本与段偏移，否则读侧只能靠猜 |
| docs 段 | 文档数 × `u32`，doc_id 升序去重 | = 第 7.1 节的文档表（先只存 doc_id；title / offset / length 等有了语料再加） |
| terms 段 | 每条：`u32 df`、`u32 tf`、`u64 postings 偏移`、`u16 词干长度`、词干字节；整体按词干升序 | = 第 7.2 节的词典，但**整表驻留内存**重建哈希表（真实语料 V ≈ 3×10^4，代价可忽略） |
| postings 段 | `[doc 增量][该文档的位置数][位置增量 × 位置数]` 重复 df 次，全部 LEB128 | = 第 7.3 节的 gap + varint，**已实现**；分块 + skip 指针仍留到 M4 |

```
头部 64 B：u64 文档数 / 词条数 / 位置总数、u64 docs / terms / postings 偏移 …
docs：     文档数 × u32（doc_id 升序去重，给 df/N 提供 N）
terms：    u32 df + u32 tf + u64 偏移 + u16 词干长度 + 词干字节（按词干升序）
postings： [doc 增量][该文档位置数][位置增量 × 位置数] 重复 df 次，LEB128
```

实现要点与取舍：

- **定长整数一律小端、宽度固定，不 dump 结构体**：结构体的 padding、`int` 宽度、字节序都进不了文件。
- **词条按词干升序**：输出与哈希桶顺序无关，同一份输入永远得到**逐字节相同**的 `index.bin`（可复现、可 diff）。
- **`df` / `tf` 冗余写进词典**：加载时用解出的组数 / 位置数交叉校验，所有词条的合计必须等于头部的
  位置总数、`postings` 段末尾必须正好是文件末尾。这些校验是**必需的**：一个被改坏的头部数字
  能让 `query` 按垃圾长度分配内存、或顺着垃圾偏移读到天荒地老。加载前还会先 `fseek` 到末尾拿文件
  长度，校验段偏移递增、各段长度不越界、词条数不超过「terms 段字节数 / 18」。
- **先写 `index.bin.tmp` 再 `rename()`**：写一半失败（磁盘满 / 被中断）不会留下半截索引被当成有效文件读入；
  `index_save()` 的返回值、`fclose()` 的返回值、`ferror()` 都要检查，失败就删掉 `.tmp` 并报错退出。
- **加载后必须能重建出一模一样的索引**：`index_load()` 用 `index_add_position()` 插回内存，
  和 `index_build()` 是同一个入口（见第 12 节的实测）。
- **已知局限：v1 没有校验和。** 改坏一两个字节、但改完仍然「结构自洽」的文件会被照常接受
  （实测：把某个位置条目的 doc_id 改成另一个已存在的文档，结构仍自洽 → 加载成功）。根治办法是在
  头部加校验和字段（头部现在正好用满 64 B，要扩到 72 / 80 B 并递增版本号）。取舍：索引由自己的程序
  生成、可随时重新生成，校验和的收益只在「手工篡改文件」这一种场景，所以留作 v2 可选项。
- **与第 7.2 节的差距**：整表驻留内存的词典在 V = 4×10^8 时会占十几 GB，所以 Bonus 路径必须换成
  「分块 + 前缀压缩 + 稀疏索引」，届时 `index_load()` 也要改成按需读块。
- **改格式要改 `index.h` 一处**：规范注释、`index_save()`、`index_load()` 现在都在同一个文件里；
  但因为有 `index_gen` / `query` 两份编译副本，改完必须重跑 `tests/run_tests.sh`（往返 `cmp` +
  独立对拍是唯一的结构性守卫），并重新跑一次 `./index_gen`。当前 `index_load()` 要求 `version == 1` 且 `header_size == 64`，
  所以现在动头部任何一处都算破坏性改动（必须同步递增版本号）；想让老文件继续可读，
  得把校验改成「版本相同且头部长度 ≥ 自己需要的最小长度」，多出来的字节当保留区跳过。

## 6. 两种语料的量级差与文档粒度

| | 真实语料（莎士比亚全集） | Bonus 目标 |
| --- | --- | --- |
| 文档数 N | ~40（37 部剧 + 十四行诗 + 叙事诗） | 500,000 |
| 总词次 | ~9×10^5 | ~10^10（按每篇 20,000 词估） |
| 不同词数 V | ~3×10^4（小写后、词干化前） | 400,000,000 |

两者差 4 个数量级。所以方案分两层，**共用同一套接口**、只换后端实现：

- **内存后端**（已实现）：用于真实语料（峰值内存几十 MB，实现简单、便于对拍）；
- **磁盘后端**（第 8、11 节）：用于 Bonus 规模（内存上限固定，与 N、V 都无关）。

### 6.1 文档粒度：按「一部剧」还是按「一幕」

题面只说 *returns the IDs of the documents*，没规定 document 的粒度。两种取法的实现差别：

| | 按剧（play） | 按幕 / 场（act / scene） |
| --- | --- | --- |
| 文档数 N | ~40 | ~200（幕）/ ~1000（场） |
| 切分成本 | **零**：`shakespeare.mit.edu` 上一部剧就是一个页面，一文件 = 一篇文档 | 要额外解析 `ACT I` / `SCENE 1` 标记，多一个解析函数 |
| 单篇长度 | 长（一部剧 2–3 万词） | 短（一幕 3–5 千词，一场几百词） |
| 总词次 | 不变 | 不变 |
| postings 总条数 | 少 | **多**（同一个词分散命中更多文档）→ 索引体积上升 |
| 每个 postings 列表 | 长 | 短（求交更快） |
| `df / N` 的语义 | 分母小，阈值 θ 相对更"严" | 分母大 → **同一个词更容易越过 θ**；幕很短，功能词几乎幕幕出现 → stoplist 明显变长 |
| 查询结果 | 「36 部剧中的 12 部」，粒度符合直觉 | 「第 3 幕第 2 场」，更细但很碎 |
| 短语查询 | 若位置编号跨场景不重置，会把跨场景的词误判成连续 | 幕内位置天然连续，语义更干净 |
| 离 Bonus 的距离 | N 太小，不会暴露「文件数爆炸」的问题 | 更接近 Bonus 形态（文件多、单文件小），M4 路径更自然 |

**建议：主实现按剧，但把粒度做成参数 `--granularity=play|act`。** 理由：

1. 索引层完全不用改，只在解析层多一个函数；
2. 给第 4 问的阈值实验**多一个维度**（θ / τ 与 N 的交互），报告里可直接对比同一批查询在 N=40 与 N=200 下的差异；
3. 给 Bonus 的讨论提供实测数据（把 N 从 40 提到 1000，观察 `df / N` 曲线与索引体积变化）。

## 7. 目标数据模型（Bonus 规模怎么存）

第 5 节是已落地的 v1；本节是它要演进成的完整形态（面向 4 亿词的 Bonus 目标）。

### 7.1 文档表 `DocTable`

`(docid, title, offset, length)` 的追加表，docid 从 0 递增。

- 真实语料：内存数组，40 条。
- Bonus：`uint32_t docid`（500,000 < 2^32）。文档表落盘 `500,000 × 64 B ≈ 32 MB`，常驻内存也可以接受。

### 7.2 词典 `TermDict`：`term -> (termid, df, postings 偏移, postings 字节长)`

- **真实语料**：开放寻址哈希表，key 用 `strdup` 存（当前实现即此）。
- **Bonus（4 亿词）**：**不能**用内存哈希表。粗算：4×10^8 × 约 20 B ≈ 8 GB，算上装填因子要 16 GB。
  改成 **排序 + 分块压缩词典（SSTable 风格）**：
  - 磁盘上是按 term 排序的块，每块 64 个 term，块内**前缀共享**（front coding）+ 变长编码；
  - 内存只驻留**稀疏索引**：每块首 term → 文件偏移。条目数 4×10^8 / 64 = 6.25×10^6，约 100 MB；
  - 查询：稀疏索引二分定位块 → 读 1 个块（~1 KB）→ 块内顺序扫。
  - 收益：常驻内存从 ~10 GB 降到 ~100 MB。

### 7.3 倒排表 `Postings`

每个 term 一个**有序**的 docid 列表（外加 tf；短语查询还需要位置）。

- **编码**：docid 用 **gap + varint（LEB128）**（v1 已实现）。相邻命中文档的平均间隔小，多数 gap 落在 1 B。
  总 posting 数 ~10^10 → 约 **10 GB**（落盘）；真实语料只有几 MB。
- **分块 + skip**：每 128 个 posting 一块，块头记该块首个 docid，支撑求交时跳跃前进。
- **求交**：较小 df 优先 + skip 跳跃；短语查询先取交集，再用位置列表验证连续性。
- Bonus 规模下 **docid/termid 都用 `uint32_t`**，文件偏移用 `uint64_t`（10 GB > 4 GB）。

### 7.4 停用词表

见第 9 节。实现上是 termid 的位图 / 哈希集合，建索引时跳过。

## 8. 建索引流程（SPIMI）

```
（可选）pass 1：扫描全部文档 -> 统计每个 term 的 df -> 写出 stoplist
pass 2：
    for each file:
        tokenize（按 isalnum 连续段切）-> tolower -> stemword()
        跳过 stoplist 中的 term
        产出 (term, docid, tf, positions)
    写入内存缓冲（SPIMI）：
        缓冲达到上限（如 256 MB）-> 按 term 排序 -> 写出一个有序 run
    最后 k 路归并所有 run -> 最终倒排索引
```

要点：

1. **切词**：按 `isalnum` 连续段切（与 hw3 同款约定）。`don't` → `don` / `t`，
   `well-known` → `well` / `known`；纯数字串也按题面当词处理。
   这套口径写在 `index_gen.c` 的切词段注释里（原 `tokenize.h`）。**切词这一层不做词干化**，
   只输出转小写后的原形：词干化全流程只由 `stemword()` 做一次（`index_gen` 建索引时一次、
   `query` 查词时一次）。Porter 不幂等（实测 604 个词里 11 个二次切会变，
   如 `because` → `becaus` → `becau`），两层各切一次会让索引与查询对不上。
2. **词干化**：索引 key 存的是**词干**，不是原形。查询词也走同一个 `stemword()`。
   可选：额外存 `stem -> 原形集合` 用于展示，但 **Bonus 规模下要砍掉**（额外内存换不来分数）。
3. **SPIMI 的收益**：内存上限由「缓冲上限 + 归并的 k 个读缓冲」决定（几百 MB），
   而**不再由 V 或 N 决定**。这是 Bonus 能否成立的关键。
4. **停用词必须在同一次建索引里产生**（df 是语料相关量，不能硬编码）。两遍扫描是最直接的实现；
   如果只想扫一遍，退化方案是「固定表 + 落盘时按 df 截断 postings」。

## 9. 停用词：线画在哪里（题面第 1 问）

题面原话是 *"How and where do you draw the line between 'interesting' and 'noisy' words?"*
—— **这句话本身就是要求：必须给出可复现的量化准则，并讨论它的代价。**

| 准则 | 定义 | 优点 | 代价 |
| --- | --- | --- | --- |
| A. 固定表 | 经典 ~300 个英文功能词 | 简单、可复现、与语料无关 | 语料相关的噪声词漏掉（莎士比亚里的 `thou` / `thee` / `hath` / `doth` 不在表里） |
| B. 全局频次 cf | 总词次 top-K，或 `cf / 总词次 > θ` | 不需要文档粒度统计 | 会误杀「高频但有区分度」的词（某部剧里反复出现的角色名） |
| **C. 文档频率 df** | `df(term) / N > θ`，df = **含该词的文档数** | IR 里的标准做法：它衡量的正是「这个词能不能区分文档」 | 需要一次全语料统计（多扫一遍） |

**推荐 C（df）为主 + A 兜底：**

- `df / N` 接近 1 的词，几乎出现在每一篇文档里 → 对「哪些文档含它」没有信息量 → 噪声。
- 默认阈值取 **θ = 0.5**（超过一半文档都含它就判噪声），再叠加固定表兜底。
- 报告里应给出 θ ∈ {0.3, 0.4, 0.5, 0.6} 时 stoplist 大小与查询结果的变化 —— 这正是第 4 问的素材。

**已落地**：pass 1 的 `wc_scan()` 用与建索引完全相同的入口统计 cf / df，`wc_stoplist()` 按
`df/N > θ` 挑出停用词写进 `stoplist.txt`，pass 2 建索引时跳过它们；`./index_gen --count-only`
会打印完整词频报告（N、V、总词次、stoplist 明细、cf 前 50 名），即"第 1 问"的原始数据。
`tests/sweep.py` 在合成语料（N=40）上的实测：

| θ | stoplist 条数 | 索引词条数 | index.bin | 保留的位置条目 |
| --- | --- | --- | --- | --- |
| 0.3 | 733 | 6391 | 235.2 KB | 14.2% |
| 0.4 | 532 | 6592 | 252.2 KB | 16.4% |
| 0.5 | 422 | 6702 | 263.8 KB | 18.1% |
| 0.6 | 340 | 6784 | 274.3 KB | 19.7% |

代价要写在报告里：θ 越小删得越狠，索引越小、查询越快，但**含停用词的短语会查不到**
（`"to be or not to be"` 五个词全在 stoplist 里 → 必然 0 命中），这是剔除停用词的固有副作用；
索引侧能做的补救是让 `query` 用 `stoplist.txt` 明确回答"这是 Part 1 剔除的停用词"，
而不是笼统的 `Not found`。

## 10. 查询与阈值（题面第 3、4 问）

接口：`query <word>...`，返回含该词（或含全部词的交集）的 docid 列表。

阈值要处理两类问题：

1. **入索引前的阈值**：`df / N > θ` 的词不进索引（第 9 节）。
2. **查询时的阈值**：df 仍偏高的词（比如 `df / N = 0.3`）会让结果集大到没有意义。两种做法：
   - **硬阈值**：`df / N > τ` 时直接返回 `term is too common, N documents` 并提示；
   - **软阈值**：返回 **top-K**（K 由用户给），按 tf-idf / BM25 排序，而不是全量返回。
     Bonus 规模下这是**唯一可行**的做法（原因见第 11 节）。
3. **短语查询**：需要位置索引 `(docid, [pos...])`。先对最稀有的词取候选文档，再逐文档验证位置连续。
   真实语料可以做（位置链已就绪）；Bonus 规模下位置索引体积翻倍，建议做成可选开关。

报告里给出 τ 的敏感性实验：同一批查询下，`τ` 与「平均结果集大小」「人工判定相关的前 20 条被截掉多少」的关系。

**已落地**：`query` 实现单词 / 多词 AND / 短语三种查询。短语走"先对各词取文档交集、再逐候选文档
用位置链验证 `pos, pos+1, pos+2...` 连续"，并用 **tf 最小的词当锚点**（候选起始位置最少，
验证代价最低）。查询阈值 τ 是**硬阈值**：`df/N > τ` 时打印

```
Too common: wevafi  (df=18/40 = 0.450, tf=27, tau=0.200 -> 18 documents, result list suppressed)
```

并在多词查询里把该词排除出交集，让"阈值如何改变结果"直接看得见。

实测（合成语料，N=40，索引用 θ = 0.5 建；`tests/sweep.py`）：

| τ | 高频词 df/N=0.450 | 中频词 df/N=0.200 | 极稀有词 df/N=0.025 | 被拦下的查询 |
| --- | --- | --- | --- | --- |
| 不设 | 27 篇 | 11 篇 | 1 篇 | 0/3 |
| 0.1 | 拦下 | 拦下 | 1 篇 | 2/3 |
| 0.2 | 拦下 | 11 篇 | 1 篇 | 1/3 |
| 0.3 | 拦下 | 11 篇 | 1 篇 | 1/3 |
| 0.4 | 拦下 | 11 篇 | 1 篇 | 1/3 |

两点结论：① τ 只有落在 `(0, θ]` 内才有效 —— `df/N > θ` 的词在 Part 2 就已经不在索引里，
查询侧只会得到 `Not found`（还会被提示成停用词），所以"查询阈值"的可用区间其实由建索引时的 θ 决定；
② 硬阈值的价值是让"结果集大到没有意义"变成一句可解释的提示，代价是**完全丢掉**该词的结果列表，
真实系统应当用软阈值（top-K + tf-idf / BM25，见第 11 节）。

## 11. Bonus：500,000 文件 / 400,000,000 词

**结论：现在这份代码不能；换成第 7、8 节的结构后能，但代价是索引必须落盘。**

### 11.1 先把账算出来

| 项 | 估算 |
| --- | --- |
| 词典（内存哈希表） | 4×10^8 × ~20 B ≈ 8 GB，含装填因子 ~16 GB |
| postings 裸存（4 B/条） | 10^10 × 4 B = 40 GB |
| postings 压缩后（delta + varint） | ≈ 10 GB |
| 文档表 | 500,000 × 64 B ≈ 32 MB（可忽略） |

→ 索引总量 **10–20 GB**，**必须落盘**。「全内存 + 定长数组」在这里完全不成立。

### 11.2 为什么这些写法会当场死

下表是已删除的旧 `mini_search_engine.c` 骨架里的写法，留作对照：

| 旧写法（已删除） | 尺寸 | 问题 |
| --- | --- | --- |
| `FileNode *file_list[5000000]` 嵌在 `WordCount` 里 | 38.1 MB / 条 | 词表里**每个词**都要背 38 MB，V = 4 亿不可能 |
| `WordCount *words[400000000]` | 2.98 GB | 按「词数上限」而不是「实际词表大小」开数组，内存不可控 |
| 每个 term 独立 `malloc` 一块 postings | — | 4 亿次 malloc + 指针追逐，cache 全废 |
| 全量读入内存后排序 | — | 峰值内存 = 全语料 |

### 11.3 能跑的做法（本方案）

1. **SPIMI / BSBI 外部归并建索引**（第 8 节）：内存上限固定，与 V、N 无关。
2. **磁盘倒排 + delta/varint + 每 128 条一个 skip 指针**：10^10 posting ≈ 10 GB，顺序读友好。
3. **排序块压缩词典 + 内存稀疏索引**：常驻内存从 ~10 GB 降到 ~100 MB。
4. **查询用 top-K（WAND / MaxScore）而不是全量返回**：高 df 词不再炸出百万结果。
   这也是第 10 节的「查询阈值」在 Bonus 规模下的必然形态。
5. **`uint32_t` 装 docid / termid**，文件偏移用 `uint64_t`，落盘长度用变长编码。
6. **`mmap` + 顺序扫描**，不要 4 亿次小 `read()`。
7. **可选的更深一层**：若 10 GB 仍放不下，把 postings 按 term 哈希分片成 P 个桶，各自独立建索引 / 查询
   （query 只打需要的桶）。代价是复杂度上升。

### 11.4 分阶段实现路径（建议按此顺序）

| 里程碑 | 内容 | 验收标准 |
| --- | --- | --- |
| **M1** | 单文件词计数：`isalnum` 切词 + tolower + `stemword`；用**可增长**哈希表 + 动态 postings 数组 | 与 `tr -cs 'A-Za-z0-9' '\n' \| sort \| uniq -c` 逐行一致 |
| **M2** | 多文件 + docid 表 + pass 1 统计 df + 停用词阈值 θ | 倒排索引与 Python 暴力参考实现逐 term 完全一致 |
| **M3** | 查询程序：单词 / 交集 / 短语；τ 阈值实验 | 查询结果与暴力实现一致；产出 θ / τ 敏感性曲线 |
| **M4（Bonus）** | SPIMI 外部归并 + varint/skip + 块压缩词典；用脚本生成的 50 万小文件跑通 | 峰值 RSS 与语料规模无关（曲线是平的）；索引落盘后可重新加载并查询 |

## 12. 测试：结果与验证

测试入口是 [`tests/run_tests.sh`](tests/run_tests.sh)：在临时目录里编译四个程序、生成合成语料，
然后逐项校验，当前 **21 项全部 PASS**（合成语料：40 篇 / 161,892 条三元组 / N=40 / V=7,124 / θ=0.5）。

**编译与静态检查**

- 四个程序（`index_gen` / `query` / `stem_list` / `roundtrip`）在
  `-std=c99 -Wall -Wextra -Wpedantic` 下**零告警**；`tests/run_tests.sh` 第 1 步就是这条。
  交付的两个源文件是 `index_gen.c` 与 `query.c`（各链 `stem.c`），`stem_list` / `roundtrip`
  只是 `tests/` 下的测试工具。

**倒排索引正确性（Testing 2 分）**

- **独立对拍（最强的一条）**：`tests/brute_check.py` 用另一份实现（Python 按 `index.h` 规范重新解析
  `index.bin`，含 LEB128 解码）与"从 `--dump-tokens` 写出的三元组流暴力聚合"的结果逐词条比较
  —— 词条集合、df、tf、完整位置链全部相等：`PASS: 6702 terms, 29296 positions, 40 documents`。
  同时验证结构自洽：魔数 / 版本 / 段偏移递增 / terms 段长度 / 各词条 df·tf / 位置总数 /
  文件末尾无多余字节。
- **停用词确实不在索引里**：同一脚本加 `--stoplist`，要求索引恰好等于「全部词条 − stoplist」。
- **编解码往返**：`tests/roundtrip.c` 读 `index.bin` → `index_load()` → `index_save()`
  再写一份，与原文件 `cmp` **逐字节相同**（这条测试在开发时抓到过"魔数按 8 字节读字符串字面量"的 bug）。
- **切词口径对拍**：`./index_gen --dump-tokens=file.txt` 在样例文档上的词表与
  `tr -cs 'A-Za-z0-9' '\n' | tr 'A-Z' 'a-z'` 逐词一致（4,057 个词）；另外
  `./index_gen --count-only --dump-tokens=... - < corpus/doc_000.txt`（stdin 一篇文档）
  写出的三元组与文件版逐字节相同。
- **短语查询对拍**：暴力枚举短语
  `zolkim vireth qandel brusett nomin` 的 (doc, start)，与 `query` 的输出一致（doc 0 与 doc 3 的 pos=10）。
- **损坏文件必须被拒绝**：截断 1 字节 / 版本号改成 2 / 纯垃圾文件，`index_load()` 全部返回 NULL、
  `query` 非零退出。已知例外见第 5 节末尾（v1 无校验和）。
- **边界：空文档 / 空索引** —— 空文档文件仍然是一篇文档（`N=1`），产出只有头部 + docs 段
  （68 字节）的索引，`query` 正常报 `Not found`；另外手工构造的 `N=0` 空索引（64 字节）
  也必须能被 `index_load()` 接受。
- 未做：**增量更新测试**（加一篇文档后只有该文档的 `(term, docid)` 变化）—— 当前实现是全量重建，
  增量能力本来就不在题面范围内。

**查询阈值（Testing 2 分）**

- `tests/sweep.py` 输出两张 Markdown 表：θ ∈ {0.3,0.4,0.5,0.6} 的 stoplist 大小 / 索引体积 /
  保留的位置比例（第 9 节），以及 τ ∈ {不设,0.1,0.2,0.3,0.4} 下三个查询的结果集大小与被拦下比例（第 10 节）。
- 结论：τ 的有效区间是 `(0, θ]`；硬阈值让"结果过大"变得可解释，但会完全丢掉该词的结果列表。

**还没做的验证**

- **真实语料上的端到端**：莎士比亚全集未下载（按指示先不做）。现有实测都在确定性合成语料上，
  换成真实语料只是把命令行里的语料换成莎士比亚的文本，测试脚本不需要改。
- **Bonus 验证**（50 万个小文件、峰值 RSS 是否为常数）：见第 11 节，属于加分项，尚未实现。

   （类型 / 接口 / 格式规范 / 全部实现）放在 `index.h`，实现写成 `static inline`，各 `#include` 一次。

   在同一次调用链上，这些约定连同 `fscanf` 的 `feof` 陷阱、残缺行截断一起消失了。

5. **遗留**：`hw3.c` 里内联的那份 `isDoubleConsonant()` 存在同一个越界读，本仓库尚未修改 `hw3.c`
   （等你的指示）。

## 14. 注意事项（踩过的坑）

- `inverted_index` 约 7.6 MB，**必须堆分配**（`index_create()`），放栈上必段错误；
- 索引所有权单一：`index_create()` 建、`index_free()` 释放（连结构体本身一起 `free`）；
- 不要把索引定义成函数的局部变量再把 `buckets` 返回出去 —— 返回的是失效的栈地址，
  类型也对不上（`Posting **` vs `Posting *`）；
- **魔数要写成 8 字节数组，不要写成字符串字面量**：`"PR1IDX"` 只占 7 字节（含结尾 `'\0'`），
  按 8 字节读写会越界读到字面量之后的字节。这个 bug 在开发时真的踩到了：同一份数据两次落盘的第 8
  个字节不同，靠「往返后 `cmp`」才发现 —— 所以第 12 节那条往返测试是必需的，不是锦上添花；
- C99 标准里没有 `strdup`（那是 POSIX，隐式声明返回 `int` 会截断 64 位指针），
  所以 `index.h` 里自己写了 `dup_string()`（两个程序共用同一份，不各自实现）；
- **`index.h` 里的实现是 `static inline`**：两个程序各编译一份副本，所以某个程序用不到的
  那一半（比如 `query` 用不到 `index_save`）不会触发 `-Wunused-function` —— 写成普通 `static`
  就会被 `-Wall -Wextra` 判为"定义未使用"。改 `index.h` 里的任何实现都要意识到它同时影响两个程序；
- `stemword()` **原地改写**缓冲区，不要传字符串字面量或 `const char *`；`query.c` 的
  `term_resolve()` 因此先把查询词拷进本地缓冲再词干化；
- 单独用 `stem()` 时：调用前要自己统一大小写（它只对小写字母序列有效），调用后要自己补 `'\0'`
  （它返回词干末字符的下标，不写结束符）；`stem()` 内部用文件级静态变量，不可重入、非线程安全。

**实现完成后新踩到的坑（都是这次加 Part 1/3/4 时才发现的）**

- **Porter 不幂等，所以切词层绝不能词干化**：`stemword()` 全流程只能做两次（建索引一次、查询一次）。
  实测 604 个词里有 11 个二次切会变（`because` → `becaus` → `becau`、`release` → `releas` → `relea`）；
  切词层（`tokenize_document()`）一旦先词干化，建索引/查询时就会再切一次，索引里存 `becau`、
  查询侧得 `becaus`，**查不到且索引文件本身完全合法**。所以这一层只做 `tolower`，
  而且这条约束现在由"切词与建索引在同一次调用链上"直接保证，不再依赖两个程序之间的接口约定。
- **停用词会让"含停用词的短语"必然查不到**：`"to be or not to be"` 五个词全在 stoplist 里，
  索引里没有它们，短语检查连候选文档都取不到。这不是 bug 而是取舍（第 9 节），
  报告里必须写明；`query` 能做的补救是用 `stoplist.txt` 把 `Not found` 解释成"Part 1 剔除的停用词"。
- **τ 的可用区间被 θ 限制**：`df/N > θ` 的词已经不在索引里，查询侧根本看不到它们的 df，
  所以 τ 只有落在 `(0, θ]` 内才有意义；把 τ 设成 0.6 而 θ 还是 0.5 时，什么都不会被拦下。
- **`isalnum()` / `tolower()` 必须先把 `char` 转成 `unsigned char`**：直接传 `char`（在 x86 上是有符号的）
  遇到非 ASCII 字节（比如 UTF-8 中文、`naïve` 的 `ï`）是越界访问，UB。`index_gen.c` 的
  `tokenize_document()` 里所有 `ctype` 调用都写了 `(unsigned char)` 转换。
- **求交的循环每轮都必须让锚点前进**：`intersect_docs()` 在"锚点词不匹配"的分支里也要推进 `pos[0]`，
  否则两边的指针都不动 → 死循环。这里用"把锚点跳到 ≥ 对方当前 doc 的第一个位置"来保证严格前进。
- **短语验证要用 tf 最小的词当锚点**：`run_phrase_query()` 会就地重排 `terms[]`（按 tf 升序），
  所以调用方若要按用户输入的顺序打印词，必须在调用**之前**打印完 —— `query.c` 就是这么做的。
- **超长词的截断口径现在只有一处**：超过 `TOKEN_MAX-1` 字节的 `isalnum` 段一律按 `TOKEN_MAX-1`
  截断，截断发生在 `tokenize_document()` 里，同时决定入库的词干和 `--dump-tokens` 写出的词形，
  不会再有"写出去的和读回来的词边界不一致"这类问题（原来还要照顾 `fscanf("%255s")` 的口径）。
