## 1. 本目录是什么

代码按题面的「三个程序」拆分（2026-09-26）：word counting / index generation / query processing
在评分细则里是**三个程序**，且第 3 问要求 *"query program on top of your **inverted file** index"*
—— 索引要落盘、查询程序独立读盘。所以本目录的结构是「建索引程序 + 查询程序」，中间靠 `index.bin` 连接。

**现状：端到端已经打通。** `index_gen` 读三元组建内存倒排索引 → 写 `index.bin`；
`query` 独立加载 `index.bin` → 查词 → 写 `output.txt`。
实测（本机 gcc 11 / x86-64，880,000 条三元组 / 40 篇文档 / 26,376 个词干）：建索引 + 落盘约 1.3 s、
峰值内存约 39 MB，`index.bin` 约 3.6 MB，`query` 加载 + 查询约 0.13 s。

**剩下的阻塞项**（按依赖顺序）：

1. `wordcount` 的 stoplist —— 题面明写 *The stop words identified in part (1) must not be included*，
   现在索引里还带着停用词；
2. `tokenize` 的切词口径 —— 现在靠外部生成的「`<word> <doc_id> <pos>`」文件喂数据；
3. `query` 的短语查询与 τ 阈值。

## 3. 构建与运行

```bash
# 建索引：读 file.txt -> 建内存倒排索引 -> 写 index.bin
gcc -std=c99 -Wall -Wextra -o index_gen index_gen.c index_io.c stem.c -lm
./index_gen

# 查询：读 index.bin -> 查词 -> 写 output.txt
gcc -std=c99 -Wall -Wextra -o query query.c index_io.c stem.c -lm
./query run zebra          # 直接查命令行给出的词
./query                    # 不给参数则读 test.txt（按空白切词）
```

两个程序只用**当前工作目录**下的相对路径（`file.txt` / `index.bin` / `test.txt` / `output.txt`），
不认命令行里的路径参数；数据文件与可执行文件放在同一个目录即可。若还没有 `index.bin`，
`./query` 会提示先跑 `./index_gen`；若 `index.bin` 损坏或版本不符，`./query` 会拒绝加载并报错
（不会带着半个索引继续查）。

注意：仓库根目录的 `stmr.c` / `stmr.h` 是算法上游对照，**不要**和 `stem.c` 一起编译
（`stem` 符号会重复定义）。

## 4. 数据流与已实现的索引结构

```
file.txt ──index_gen──> 内存倒排索引 ──index_save()──> index.bin
                                                        │
test.txt ──────────────────────> query ──index_load()───┘ ──> output.txt
```

内存结构（在 `index_io.c` 里，`index_gen` 与 `query` 共用）：

- **`djb2` 哈希**（`hashsize` = 1000007 个桶）+ 链地址法；每个词干一个 `Posting`，
  挂一条按 `(doc_id, pos)` **升序**的 `Position` 链 —— df、求交、短语验证都依赖这个有序性；
- **去重键是 `(词干, doc_id, pos)`**：同一文档同一位置的同词干只保留一条；
- **词干化在建索引时做**（`stemword()` = 转小写 + Porter），所以 `run` / `runs` / `running` / `RUNS`
  并入同一个词干 `run`；查询词走同一个函数，因此查 `Running` 也能命中；
- 读入用 `while (fscanf(...) == 3)`，`doc_id` / `pos` 为负的行跳过并计数。

实测一个关键尺寸（本机 gcc 11 / x86-64）：

- `sizeof(inverted_index)` = **8,000,056 B ≈ 7.6 MB** —— `buckets` 是嵌在结构体里的定长数组。
  **必须堆分配**（`index_create()`）：放栈上会和调用者栈帧一起超过默认 8 MB 栈上限，直接段错误（已实测崩溃）。

## 5. 索引文件格式 `index.bin`（v1，已落地）

**权威规范是 `index.h` 顶部注释**，读写两侧都以那份注释为准；本节说明它的形状与取舍。

| 区段 | 内容 | 与目标设计的关系 |
| --- | --- | --- |
| 头部 64 B | 魔数 `PR1IDX`、版本、头部长度、文档数 / 词条数 / 位置总数、docs / terms / postings 三段偏移 | 设计稿里没写头部；落盘格式必须有版本与段偏移，否则读侧只能靠猜 |
| docs 段 | 文档数 × `u32`，doc_id 升序去重 | = 第 7.1 节的文档表（先只存 doc_id；title / offset / length 等有了语料再加） |
| terms 段 | 每条：`u32 df`、`u32 tf`、`u64 postings 偏移`、`u16 词干长度`、词干字节；整体按词干升序 | = 第 7.2 节的词典，但**整表驻留内存**重建哈希表（真实语料 V ≈ 3×10^4，代价可忽略） |
| postings 段 | `[doc 增量][该文档的位置数][位置增量 × 位置数]` 重复 df 次，全部 LEB128 | = 第 7.3 节的 gap + varint，**已实现**；分块 + skip 指针仍留到 M4 |

```
头部 64 B：u64 文档数 / 词条数 / 位置总数、u64 docs / terms / postings 偏移 …
docs：     文档数 × u32（doc_id 升序去重，给 df/N 提供 N）
terms：    u32 df + u32 tf + u64 偏移 + u16 词干长度 + 词干字节（按词干升序）
postings： [doc 增量][该文档位置数][位置增量 × 位置数] 重复 df 次，LEB128
```

实现要点与取舍：

- **定长整数一律小端、宽度固定，不 dump 结构体**：结构体的 padding、`int` 宽度、字节序都进不了文件。
- **词条按词干升序**：输出与哈希桶顺序无关，同一份输入永远得到**逐字节相同**的 `index.bin`（可复现、可 diff）。
- **`df` / `tf` 冗余写进词典**：加载时用解出的组数 / 位置数交叉校验，所有词条的合计必须等于头部的
  位置总数、`postings` 段末尾必须正好是文件末尾。这些校验是**必需的**：一个被改坏的头部数字
  能让 `query` 按垃圾长度分配内存、或顺着垃圾偏移读到天荒地老。加载前还会先 `fseek` 到末尾拿文件
  长度，校验段偏移递增、各段长度不越界、词条数不超过「terms 段字节数 / 18」。
- **先写 `index.bin.tmp` 再 `rename()`**：写一半失败（磁盘满 / 被中断）不会留下半截索引被当成有效文件读入；
  `index_save()` 的返回值、`fclose()` 的返回值、`ferror()` 都要检查，失败就删掉 `.tmp` 并报错退出。
- **加载后必须能重建出一模一样的索引**：`index_load()` 用 `index_add_position()` 插回内存，
  和 `index_build()` 是同一个入口（见第 12 节的实测）。
- **已知局限：v1 没有校验和。** 改坏一两个字节、但改完仍然「结构自洽」的文件会被照常接受
  （实测：把某个位置条目的 doc_id 改成另一个已存在的文档，结构仍自洽 → 加载成功）。根治办法是在
  头部加校验和字段（头部现在正好用满 64 B，要扩到 72 / 80 B 并递增版本号）。取舍：索引由自己的程序
  生成、可随时重新生成，校验和的收益只在「手工篡改文件」这一种场景，所以留作 v2 可选项。
- **与第 7.2 节的差距**：整表驻留内存的词典在 V = 4×10^8 时会占十几 GB，所以 Bonus 路径必须换成
  「分块 + 前缀压缩 + 稀疏索引」，届时 `index_load()` 也要改成按需读块。
- **改格式要同时改三处**：`index.h` 顶部注释（规范）、`index_io.c` 的 `index_save()` / `index_load()`，
  并重新跑一次 `./index_gen`。当前 `index_load()` 要求 `version == 1` 且 `header_size == 64`，
  所以现在动头部任何一处都算破坏性改动（必须同步递增版本号）；想让老文件继续可读，
  得把校验改成「版本相同且头部长度 ≥ 自己需要的最小长度」，多出来的字节当保留区跳过。

## 6. 两种语料的量级差与文档粒度

| | 真实语料（莎士比亚全集） | Bonus 目标 |
| --- | --- | --- |
| 文档数 N | ~40（37 部剧 + 十四行诗 + 叙事诗） | 500,000 |
| 总词次 | ~9×10^5 | ~10^10（按每篇 20,000 词估） |
| 不同词数 V | ~3×10^4（小写后、词干化前） | 400,000,000 |

两者差 4 个数量级。所以方案分两层，**共用同一套接口**、只换后端实现：

- **内存后端**（已实现）：用于真实语料（峰值内存几十 MB，实现简单、便于对拍）；
- **磁盘后端**（第 8、11 节）：用于 Bonus 规模（内存上限固定，与 N、V 都无关）。

### 6.1 文档粒度：按「一部剧」还是按「一幕」

题面只说 *returns the IDs of the documents*，没规定 document 的粒度。两种取法的实现差别：

| | 按剧（play） | 按幕 / 场（act / scene） |
| --- | --- | --- |
| 文档数 N | ~40 | ~200（幕）/ ~1000（场） |
| 切分成本 | **零**：`shakespeare.mit.edu` 上一部剧就是一个页面，一文件 = 一篇文档 | 要额外解析 `ACT I` / `SCENE 1` 标记，多一个解析函数 |
| 单篇长度 | 长（一部剧 2–3 万词） | 短（一幕 3–5 千词，一场几百词） |
| 总词次 | 不变 | 不变 |
| postings 总条数 | 少 | **多**（同一个词分散命中更多文档）→ 索引体积上升 |
| 每个 postings 列表 | 长 | 短（求交更快） |
| `df / N` 的语义 | 分母小，阈值 θ 相对更"严" | 分母大 → **同一个词更容易越过 θ**；幕很短，功能词几乎幕幕出现 → stoplist 明显变长 |
| 查询结果 | 「36 部剧中的 12 部」，粒度符合直觉 | 「第 3 幕第 2 场」，更细但很碎 |
| 短语查询 | 若位置编号跨场景不重置，会把跨场景的词误判成连续 | 幕内位置天然连续，语义更干净 |
| 离 Bonus 的距离 | N 太小，不会暴露「文件数爆炸」的问题 | 更接近 Bonus 形态（文件多、单文件小），M4 路径更自然 |

**建议：主实现按剧，但把粒度做成参数 `--granularity=play|act`。** 理由：

1. 索引层完全不用改，只在解析层多一个函数；
2. 给第 4 问的阈值实验**多一个维度**（θ / τ 与 N 的交互），报告里可直接对比同一批查询在 N=40 与 N=200 下的差异；
3. 给 Bonus 的讨论提供实测数据（把 N 从 40 提到 1000，观察 `df / N` 曲线与索引体积变化）。

## 7. 目标数据模型（Bonus 规模怎么存）

第 5 节是已落地的 v1；本节是它要演进成的完整形态（面向 4 亿词的 Bonus 目标）。

### 7.1 文档表 `DocTable`

`(docid, title, offset, length)` 的追加表，docid 从 0 递增。

- 真实语料：内存数组，40 条。
- Bonus：`uint32_t docid`（500,000 < 2^32）。文档表落盘 `500,000 × 64 B ≈ 32 MB`，常驻内存也可以接受。

### 7.2 词典 `TermDict`：`term -> (termid, df, postings 偏移, postings 字节长)`

- **真实语料**：开放寻址哈希表，key 用 `strdup` 存（当前实现即此）。
- **Bonus（4 亿词）**：**不能**用内存哈希表。粗算：4×10^8 × 约 20 B ≈ 8 GB，算上装填因子要 16 GB。
  改成 **排序 + 分块压缩词典（SSTable 风格）**：
  - 磁盘上是按 term 排序的块，每块 64 个 term，块内**前缀共享**（front coding）+ 变长编码；
  - 内存只驻留**稀疏索引**：每块首 term → 文件偏移。条目数 4×10^8 / 64 = 6.25×10^6，约 100 MB；
  - 查询：稀疏索引二分定位块 → 读 1 个块（~1 KB）→ 块内顺序扫。
  - 收益：常驻内存从 ~10 GB 降到 ~100 MB。

### 7.3 倒排表 `Postings`

每个 term 一个**有序**的 docid 列表（外加 tf；短语查询还需要位置）。

- **编码**：docid 用 **gap + varint（LEB128）**（v1 已实现）。相邻命中文档的平均间隔小，多数 gap 落在 1 B。
  总 posting 数 ~10^10 → 约 **10 GB**（落盘）；真实语料只有几 MB。
- **分块 + skip**：每 128 个 posting 一块，块头记该块首个 docid，支撑求交时跳跃前进。
- **求交**：较小 df 优先 + skip 跳跃；短语查询先取交集，再用位置列表验证连续性。
- Bonus 规模下 **docid/termid 都用 `uint32_t`**，文件偏移用 `uint64_t`（10 GB > 4 GB）。

### 7.4 停用词表

见第 9 节。实现上是 termid 的位图 / 哈希集合，建索引时跳过。

## 8. 建索引流程（SPIMI）

```
（可选）pass 1：扫描全部文档 -> 统计每个 term 的 df -> 写出 stoplist
pass 2：
    for each file:
        tokenize（按 isalnum 连续段切）-> tolower -> stemword()
        跳过 stoplist 中的 term
        产出 (term, docid, tf, positions)
    写入内存缓冲（SPIMI）：
        缓冲达到上限（如 256 MB）-> 按 term 排序 -> 写出一个有序 run
    最后 k 路归并所有 run -> 最终倒排索引
```

要点：

1. **切词**：按 `isalnum` 连续段切（与 hw3 同款约定）。`don't` → `don` / `t`，
   `well-known` → `well` / `known`；纯数字串也按题面当词处理。
2. **词干化**：索引 key 存的是**词干**，不是原形。查询词也走同一个 `stemword()`。
   可选：额外存 `stem -> 原形集合` 用于展示，但 **Bonus 规模下要砍掉**（额外内存换不来分数）。
3. **SPIMI 的收益**：内存上限由「缓冲上限 + 归并的 k 个读缓冲」决定（几百 MB），
   而**不再由 V 或 N 决定**。这是 Bonus 能否成立的关键。
4. **停用词必须在同一次建索引里产生**（df 是语料相关量，不能硬编码）。两遍扫描是最直接的实现；
   如果只想扫一遍，退化方案是「固定表 + 落盘时按 df 截断 postings」。

## 9. 停用词：线画在哪里（题面第 1 问）

题面原话是 *"How and where do you draw the line between 'interesting' and 'noisy' words?"*
—— **这句话本身就是要求：必须给出可复现的量化准则，并讨论它的代价。**

| 准则 | 定义 | 优点 | 代价 |
| --- | --- | --- | --- |
| A. 固定表 | 经典 ~300 个英文功能词 | 简单、可复现、与语料无关 | 语料相关的噪声词漏掉（莎士比亚里的 `thou` / `thee` / `hath` / `doth` 不在表里） |
| B. 全局频次 cf | 总词次 top-K，或 `cf / 总词次 > θ` | 不需要文档粒度统计 | 会误杀「高频但有区分度」的词（某部剧里反复出现的角色名） |
| **C. 文档频率 df** | `df(term) / N > θ`，df = **含该词的文档数** | IR 里的标准做法：它衡量的正是「这个词能不能区分文档」 | 需要一次全语料统计（多扫一遍） |

**推荐 C（df）为主 + A 兜底：**

- `df / N` 接近 1 的词，几乎出现在每一篇文档里 → 对「哪些文档含它」没有信息量 → 噪声。
- 默认阈值取 **θ = 0.5**（超过一半文档都含它就判噪声），再叠加固定表兜底。
- 报告里应给出 θ ∈ {0.3, 0.4, 0.5, 0.6} 时 stoplist 大小与查询结果的变化 —— 这正是第 4 问的素材。

## 10. 查询与阈值（题面第 3、4 问）

接口：`query <word>...`，返回含该词（或含全部词的交集）的 docid 列表。

阈值要处理两类问题：

1. **入索引前的阈值**：`df / N > θ` 的词不进索引（第 9 节）。
2. **查询时的阈值**：df 仍偏高的词（比如 `df / N = 0.3`）会让结果集大到没有意义。两种做法：
   - **硬阈值**：`df / N > τ` 时直接返回 `term is too common, N documents` 并提示；
   - **软阈值**：返回 **top-K**（K 由用户给），按 tf-idf / BM25 排序，而不是全量返回。
     Bonus 规模下这是**唯一可行**的做法（原因见第 11 节）。
3. **短语查询**：需要位置索引 `(docid, [pos...])`。先对最稀有的词取候选文档，再逐文档验证位置连续。
   真实语料可以做（位置链已就绪）；Bonus 规模下位置索引体积翻倍，建议做成可选开关。

报告里给出 τ 的敏感性实验：同一批查询下，`τ` 与「平均结果集大小」「人工判定相关的前 20 条被截掉多少」的关系。

## 11. Bonus：500,000 文件 / 400,000,000 词

**结论：现在这份代码不能；换成第 7、8 节的结构后能，但代价是索引必须落盘。**

### 11.1 先把账算出来

| 项 | 估算 |
| --- | --- |
| 词典（内存哈希表） | 4×10^8 × ~20 B ≈ 8 GB，含装填因子 ~16 GB |
| postings 裸存（4 B/条） | 10^10 × 4 B = 40 GB |
| postings 压缩后（delta + varint） | ≈ 10 GB |
| 文档表 | 500,000 × 64 B ≈ 32 MB（可忽略） |

→ 索引总量 **10–20 GB**，**必须落盘**。「全内存 + 定长数组」在这里完全不成立。

### 11.2 为什么这些写法会当场死

下表是已删除的旧 `mini_search_engine.c` 骨架里的写法，留作对照：

| 旧写法（已删除） | 尺寸 | 问题 |
| --- | --- | --- |
| `FileNode *file_list[5000000]` 嵌在 `WordCount` 里 | 38.1 MB / 条 | 词表里**每个词**都要背 38 MB，V = 4 亿不可能 |
| `WordCount *words[400000000]` | 2.98 GB | 按「词数上限」而不是「实际词表大小」开数组，内存不可控 |
| 每个 term 独立 `malloc` 一块 postings | — | 4 亿次 malloc + 指针追逐，cache 全废 |
| 全量读入内存后排序 | — | 峰值内存 = 全语料 |

### 11.3 能跑的做法（本方案）

1. **SPIMI / BSBI 外部归并建索引**（第 8 节）：内存上限固定，与 V、N 无关。
2. **磁盘倒排 + delta/varint + 每 128 条一个 skip 指针**：10^10 posting ≈ 10 GB，顺序读友好。
3. **排序块压缩词典 + 内存稀疏索引**：常驻内存从 ~10 GB 降到 ~100 MB。
4. **查询用 top-K（WAND / MaxScore）而不是全量返回**：高 df 词不再炸出百万结果。
   这也是第 10 节的「查询阈值」在 Bonus 规模下的必然形态。
5. **`uint32_t` 装 docid / termid**，文件偏移用 `uint64_t`，落盘长度用变长编码。
6. **`mmap` + 顺序扫描**，不要 4 亿次小 `read()`。
7. **可选的更深一层**：若 10 GB 仍放不下，把 postings 按 term 哈希分片成 P 个桶，各自独立建索引 / 查询
   （query 只打需要的桶）。代价是复杂度上升。

### 11.4 分阶段实现路径（建议按此顺序）

| 里程碑 | 内容 | 验收标准 |
| --- | --- | --- |
| **M1** | 单文件词计数：`isalnum` 切词 + tolower + `stemword`；用**可增长**哈希表 + 动态 postings 数组 | 与 `tr -cs 'A-Za-z0-9' '\n' \| sort \| uniq -c` 逐行一致 |
| **M2** | 多文件 + docid 表 + pass 1 统计 df + 停用词阈值 θ | 倒排索引与 Python 暴力参考实现逐 term 完全一致 |
| **M3** | 查询程序：单词 / 交集 / 短语；τ 阈值实验 | 查询结果与暴力实现一致；产出 θ / τ 敏感性曲线 |
| **M4（Bonus）** | SPIMI 外部归并 + varint/skip + 块压缩词典；用脚本生成的 50 万小文件跑通 | 峰值 RSS 与语料规模无关（曲线是平的）；索引落盘后可重新加载并查询 |

## 14. 注意事项（踩过的坑）

- `inverted_index` 约 7.6 MB，**必须堆分配**（`index_create()`），放栈上必段错误；
- 索引所有权单一：`index_create()` 建、`index_free()` 释放（连结构体本身一起 `free`）；
- 不要把索引定义成函数的局部变量再把 `buckets` 返回出去 —— 返回的是失效的栈地址，
  类型也对不上（`Posting **` vs `Posting *`）；
- **魔数要写成 8 字节数组，不要写成字符串字面量**：`"PR1IDX"` 只占 7 字节（含结尾 `'\0'`），
  按 8 字节读写会越界读到字面量之后的字节。这个 bug 在开发时真的踩到了：同一份数据两次落盘的第 8
  个字节不同，靠「往返后 `cmp`」才发现 —— 所以第 12 节那条往返测试是必需的，不是锦上添花；
- 读文件用 `while (fscanf(...) == 3)`，不要用 `while (!feof(...))`：后者在文件末尾还会用
  上一次（首次是未初始化）的值再插一条记录；
- C99 标准里没有 `strdup`（那是 POSIX，隐式声明返回 `int` 会截断 64 位指针），
  所以 `index_io.c` 里自己写了 `dup_string()`（`index_gen.c` / `query.c` 都不再各自实现）；
- **残缺行会截断读取**：`fscanf` 遇到格式不符的行返回 1 或 2，循环立即结束，其后内容一律不再入库
  （能被跳过并计入 `invalid` 的只有 `doc_id` / `pos` 为负的行）。要容忍脏输入得改成按行读，
  这件事交给 `tokenize`；
- `stemword()` **原地改写**缓冲区，不要传字符串字面量或 `const char *`；`query_word()` 因此
  先把查询词拷进本地缓冲再词干化；
- 单独用 `stem()` 时：调用前要自己统一大小写（它只对小写字母序列有效），调用后要自己补 `'\0'`
  （它返回词干末字符的下标，不写结束符）；`stem()` 内部用文件级静态变量，不可重入、非线程安全。
